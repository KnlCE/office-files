# Проверка Office Files 0.2.0

## Тестовый чат 2026-10-26 и PDF

Чат «протестируй плагин на всех форматах» (провайдер `astra`, модель Claude) выявил три проблемы:

1. `word_create` и `powerpoint_create` — 6 отказов подряд с ошибкой `/spec: '…' is not of type 'object'`. Модель передавала `spec` строкой JSON, а `overwrite` — строкой `"true"`. Только `excel_create` получил объект. Обходной путь через общий `tool_call` сработал.
2. `office_inspect` с `path` вместо `input_path` — 2 отказа.
3. Ход закончился на 10-м раунде с текстом «нет доступа к инструментам», редактирование и конвертация остались непроверенными. 10 раундов — это `DEFAULT_TOOL_ROUNDS` сервера (`minice/api`, `astra-chat/src/budget.rs`), то есть `budget.max_tool_rounds = 24` от демона до сервера не дошёл. Это вне плагина, исправление не вносилось. Причины раундов, потраченных впустую (пункты 1–2), устранены.

Корневая причина пункта 1 на стороне хоста: для `astra`/`gemini` санитайзер схем демона (`astra-daemon/src/ai/providers/schema/gemini.rs`) выбрасывал `const`. Поэтому все варианты `oneOf` у блоков Word и объектов слайда превращались в одинаковые пустые схемы `{"type": {}}`. У Excel таких тегированных объединений на верхнем уровне нет, и он работал. Исправление в демоне: строковый `const` → `enum: [value]` + тест `const_tags_survive_as_a_one_value_enum`. Оно отдельное от плагина.

Исправления в плагине:
- `registry.normalize` (общий путь всех вызовов): строка JSON → объект/массив, `"true"`/`"false"` → boolean, числовая строка → число. Срабатывает только при несовпадении типа со схемой и успешном разборе: текстовые поля, похожие на JSON, остаются строками. `path`/`file_path`/`file`/`input` → `input_path`. Ошибка схемы выбирается через `best_match` и указывает на конкретное поле внутри `oneOf`.
- PDF: `office_inspect` (текст по страницам, метки, повороты, размеры, метаданные, оглавление, `pages_without_text` с подсказкой рендера для сканов), новый `pdf_edit` (delete/keep/rotate/move/insert_pdf, атомарно, через ревизию), `office_render` для PDF без LibreOffice. Всё на уже входившем в зависимости PDFium, новых зависимостей нет. Решение плагин vs ядро: в демоне PDF разбирается только для вложений чата (`pdf-extract`, `read_document_safe` ни откуда не вызывается). Страничные операции, рендер и общий с Office цикл inspect→revision→edit естественно живут здесь.

## Границы проверки

Linux x64 объявлен и использует POSIX process groups, переносимые библиотеки и пути, но выполнение на Linux в этой Windows-сессии не проверялось. Реальный импорт в работающий Astra UI и ручной Tool Search не выполнялись; протокол, auth и hooks проверены через официальный CLI/mock daemon и SDK WireHarness. Хост Astra, UI и SDK не изменялись, поэтому host Rust/frontend build gates не применялись к этому внешнему плагину.

SDK не передаёт отдельный cancellation token в call_tool: немедленная отмена пользователем не заявлена. Таймаут/Shutdown завершают собственное дерево процессов, включая LibreOffice. Полное семантическое сохранение неизвестных OOXML расширений не гарантируется; выявляемые неподдерживаемые элементы и потеря частей/бинарных ресурсов блокируются. Известные ограничения операций перечислены в README.

Пакет собирается официальным `astra-plugin build . --reproducible` и проверяется `astra-plugin verify`; SDK и зависимости разрешаются из requirements.lock, локальный checkout SDK не используется. В архив не входят `.venv`, тестовый LibreOffice и машинные пути. Пакет не опубликован, автор пустой, лицензия не назначена.
